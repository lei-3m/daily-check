## 1. 배경

시작점은 단순했다. **"할 일 목록을 마크다운으로 복사해서 ChatGPT에 붙여넣고 싶다."**

기존 도구들은 이 흐름에 맞지 않았다.

- Notion, Todoist 등은 복사하면 서식이 깨지거나 불필요한 메타데이터가 딸려 온다
- 메모장은 체크박스 상태 관리가 안 된다
- 대부분의 앱이 프로젝트·태그·마감일 같은 구조를 강요한다

논의를 거치며 방향이 넓어졌다. 필요한 건 체크리스트 유틸리티가 아니라 **매일 부담 없이 여는 개인 작업 공간**이다. 할 일 외에 다가오는 일정과 그날의 잡생각이 한 화면에 있어야 실제로 매일 열게 된다.

그리고 하나 더. **PC에서 적은 것이 폰에서 보여야 한다.** 하루 종일 여러 기기를 오가는 사용 패턴이라, 기기마다 내용이 다르면 신뢰할 수 없는 도구가 된다.

## 2. 목표 / 비목표

### 목표 (전부 달성)

1. 오늘 할 일을 3초 안에 적고 체크할 수 있다
2. 버튼 하나로 마크다운 체크리스트를 클립보드에 담는다
3. PC, 태블릿, 폰 어디서 열어도 같은 내용이 보인다
4. 로그인은 Google 계정 한 번. 이후 다시 묻지 않는다
5. 서버를 직접 만들거나 운영하지 않는다
6. 운영 비용 0원
7. 나중에 AI 기능을 얹을 때 UI를 뜯어고치지 않아도 되는 구조

### 비목표

- 협업, 공유, 다른 사람 초대
- 알림, 푸시
- 프로젝트·태그·하위 작업 같은 계층 구조
- 반복 일정, 캘린더 연동
- 통계, 회고, 생산성 리포트
- 실시간 동기화 (두 기기에 즉시 반영). 열 때 불러오는 수준으로 충분
- 완벽한 충돌 병합. 마지막 저장이 이기되 경고를 띄우는 방식

> 판단 기준: **"이 기능이 없으면 앱을 못 쓰는가?"** 아니라면 다음 버전으로 미룬다.

## 3. 사용자와 핵심 루프

**사용자**: 개발자 1인. **폰이 주 사용 기기.** PC에서는 ChatGPT 탭을 띄워두고 작업한다.

```
아침   앱을 연다 → 오늘이 이미 선택돼 있다
       할 일을 적는다 (여러 줄 붙여넣기도 가능)
         ↓
       📋 복사 → ChatGPT에 붙여넣기
       "이 중에 뭐부터 할까?" / "이거 어떻게 접근하지?"
         ↓
낮     돌아와서 하나씩 체크
       못 한 건 📅 다른 날짜로 → 내일
         ↓
이동중 폰에서 연다 → PC에서 적은 목록이 그대로 보인다
         ↓
저녁   메모에 한 줄 남긴다
```

### 폰이 주 기기라는 사실이 만든 차이

개발 중 반복해서 드러난 문제다. AI가 생성하는 UI는 기본적으로 **데스크톱 hover를 전제**한다. 그 결과:

- `⠿` 드래그 손잡이, `✕` 삭제 버튼이 폰에서 보이지 않았다
- 일정 삭제 기능이 있는데 없는 줄 알았다 (색이 너무 연해서)
- 모바일 키보드 엔터가 다음 입력칸으로 넘어가 할 일이 추가되지 않았다
- `＋` 버튼이 blur 때문에 동작하지 않았다

**원칙: hover에서만 나타나는 UI를 만들지 않는다.** hover 강조는 `@media (hover: hover)` 안에서만 추가로 적용한다.

## 4. 기능 명세 (구현 완료)

### 4.1 날짜 뷰

두 층으로 나뉜다.

```
주간 뷰 ──(월 이름 클릭)──▶ 월 달력
   ▲                          │
   └──────(날짜 클릭)─────────┘
```

**주간 뷰 (기본 화면)**

```
        2026년 8월 ›
  ‹   일  월  화  수  목  금  토   ›
      26  27  28  29  30  31   1
                             •   ·
```

- 일요일 시작, 토요일 끝. 항상 7칸 고정
- `‹` `›` 로 주 이동
- 요일과 일자를 두 줄로 표시
- `•` 오늘 / `·` 내용이 있는 날
- 주가 달을 걸치면 `7월 – 8월`
- 이번 주가 아닐 때만 `오늘` 버튼 표시

**왜 롤링(오늘 ±2)이 아니라 주 단위인가**

롤링은 오늘이 항상 가운데라 매일 모든 칸이 밀린다. 주 단위는 **수요일이 언제나 네 번째 자리**라 위치를 손이 기억한다. 또한 할 일 계획은 평일과 주말에 따라 완전히 다른데, `8/2`만으로는 그것이 토요일인지 알 수 없다.

**월 달력 (별도 화면)**

```
  ‹ 주간 뷰로   2026년 8월
  일   월   화   수   목   금   토
                              1
                             3/5
   2    3    4    5    6    7    8
       2/2       1/4  0/3   ·
  ─────────────────────────────
  이 달의 일정
    이번 주
      8/3   치과
      8/5   회식
    다음 주
      8/11  미용실
    그 이후
      8/20  여행
    지난 일정
      7/28  안과
```

- 할 일이 있는 날: `완료/전체` (예: `2/5`)
- 메모만 있는 날: `·`
- 아무것도 없는 날: 비움. **여백이 많은 것이 정상**
- 📌 일정이 있는 날은 셀 우측 상단에 표시
- 좌우 스와이프로 달 이동. 손가락을 실시간으로 따라오고, 화면 폭 25% 이상 또는 빠른 튕김일 때 전환
- 날짜를 클릭하면 그 날짜가 선택된 상태로 주간 뷰로 이동

**달성률(%)을 쓰지 않는 이유**

할 일 1개 중 1개는 100%, 8개 중 6개는 75%다. 바쁘게 산 날이 더 낮게 나온다. 달력을 훑을 때 이 숫자들이 성적표처럼 읽히면 앱을 여는 것 자체가 부담이 된다. `2/5`는 사실이고 `75%`는 판정이다.

**달력에 할 일을 넣었다가 뺀 이야기**

한때 달력 아래에 선택된 날짜의 할 일과 메모를 표시하고, 날짜를 클릭해도 화면에 머물도록 만들었다. 그런데 실제로 써보니 "8월 12일에 뭐 했지?"를 확인하는 일이 거의 없었다. 달력을 여는 이유는 **"이 달에 뭐 있지?"** 였다.

일정 목록이 길어지면서 할 일 영역이 화면 밖으로 밀렸고, 날짜를 눌러도 아무 반응이 없는 것처럼 보였다. 결국 할 일 영역을 제거하고 날짜 클릭 = 주간 뷰 이동으로 되돌렸다.

> **추가한 것을 도로 빼는 것이 답일 때가 있다.**

**연도 뷰는 만들지 않는다**

하루 단위 도구에 필요한 조망이 아니다. "작년 3월에 뭐 했지?"는 달력을 훑는 것이 아니라 검색으로 푸는 문제다. 다만 `View.kind` 문자열 유니온으로 자리만 열어두었다.

### 4.2 할 일

```
⠿  ☐  발표자료 만들기            ✕
⠿  ☑  PR 리뷰                   ✕
＋ 할 일 추가
```

| 동작 | 방법 |
| --- | --- |
| 추가 | 입력창에 쓰고 Enter 또는 `＋` |
| 여러 개 추가 | 여러 줄 텍스트 붙여넣기 |
| 체크 | 체크박스 클릭 |
| 수정 | 텍스트 클릭 → 인라인 편집 |
| 삭제 | 우측 `✕` 또는 빈 텍스트로 확정 |
| 정렬 | 좌측 손잡이 드래그 (dnd-kit) |

**붙여넣기 처리**: 각 줄에서 `- `, `* `, `- [ ] `, `- [x] ` 접두어를 제거한다. ChatGPT가 돌려준 목록을 그대로 다시 붙여넣을 수 있다.

**체크박스 표시를 바꾼 이유 (v0.3 → v0.4)**

원래는 마크다운 원문 `- [ ]` / `- [x]` 를 등폭 글꼴로 그대로 노출했다. 근거는 "보이는 것과 복사되는 것이 같아야 한다"였다.

논리는 맞았지만 **매일 보는 사람의 감각을 고려하지 못했다.** 매일 여는 화면이 코드 조각처럼 보이면 "부담 없이 여는 작업 공간"이라는 목표와 충돌한다.

원래 근거도 약했다. 복사 결과를 예측하는 데 마크다운 원문이 필요하지 않다. **한 번 눌러보면 알기 때문이다.**

> **복사 출력 형식은 그대로 `- [ ]` / `- [x]` 마크다운이다.** 화면 표시만 바뀌었다.

### 4.3 복사

`📋 복사` → 현재 날짜의 할 일을 마크다운으로 클립보드에 저장.

```
- [ ] 발표자료 만들기
- [x] PR 리뷰
- [ ] 운동
```

- 일정·메모는 포함하지 않는다
- `navigator.clipboard` 실패 시 `textarea` 폴백
- 완료 후 토스트

### 4.4 다가오는 일정

```
📌 다가오는 일정
   8/3   치과
   8/3   미팅
   8/5   회식
   +4개 ▾
```

- **오늘부터 7일 이내는 전부 표시.** 개수 제한 없음
- 7일 이후는 `+N개 ▾`. 누르면 **그 자리에서** 펼쳐짐
- 지난 일정은 이 블록에 표시하지 않는다. 월 달력에서 확인
- 블록 최대 높이는 화면의 약 35%. 넘치면 블록 안에서 스크롤
- 접기/펼침 상태는 앱 실행 중 유지, 새로 열면 접힘

**라벨을 "다가오는 일정"으로 바꾼 이유**

이 블록은 주간 뷰에서 어느 주를 보고 있든 **항상 오늘 기준**이다. 나란히 붙어 있어 날짜 뷰와 연동될 것처럼 보이는데, 라벨로 성격을 드러냈다.

날짜 뷰와 연동하지 않는 이유: 지난주를 잠깐 확인하러 갔는데 다가오는 일정이 사라지면 더 이상하다. 일정은 언제 봐도 "곧 있을 일"이어야 유용하다.

**개수 대신 시간으로 자르는 이유**

한때 "가장 가까운 2개"만 보여주려 했으나, 하루에 일정이 두 개 있으면 다음 날 것부터 안 보인다. **접기 기준은 오직 7일 하나**다. 개수로 자르면 어디서 잘릴지 예측할 수 없다.

### 4.5 메모

- 날짜별 자유 텍스트
- 비어 있어도 됨
- 입력 즉시 상태 반영, 디바운스 저장

### 4.6 다른 날짜로 이동

```
📅 다른 날짜로  →  선택 모드
   ☑ 발표자료
   ☑ 운동
   [8/2] [8/3] [8/8] [날짜 선택]
```

- 선택 모드에서는 완료 체크와 구분되는 선택 체크박스가 표시된다
- 빠른 버튼: 내일 / 모레 / 일주일 뒤 (현재 보고 있는 날짜 기준)
- **주 경계 처리**: 대상 날짜가 현재 주 밖이면 주간 뷰가 그 주로 자동 이동한다. 화면이 결과를 따라가지 않으면 어디로 갔는지 알 수 없다

### 4.7 로그인과 동기화

**로그인**

- Google 로그인 단일 방식
- 로그인 전에는 로그인 화면만 표시
- 세션 자동 갱신

**동기화**

- 앱을 열면 서버에서 전체 상태를 불러온다
- 변경 시 디바운스 후 서버에 전체 상태 저장
- LocalStorage는 오프라인 캐시로 유지
- **로그아웃 시 캐시를 삭제**하고, 캐시에 `user.id`를 함께 저장해 다른 사용자면 사용하지 않는다

**충돌 처리**

```
저장 직전 서버의 updated_at 확인
   ↓
서버 쪽이 더 최신이면
   → 덮어쓰지 않고 "다른 기기에서 수정된 내용이 있어요" 알림
   → [나중에] / [새로고침]
   → 덮어쓰기 전 서버 버전을 daily-check:snapshot에 보관
```

**새로고침을 누르면 현재 기기의 수정 내용이 사라진다.** 먼저 저장에 성공한 쪽이 살아남는다. 완전한 병합은 하지 않는다.

**오프라인 동작**

- 오프라인에서 수정한 내용은 LocalStorage에 즉시 저장된다. 사라지지 않는다
- 서버 업로드는 **다음 수정이 발생할 때** 함께 이루어진다
- 온라인 복귀 시 자동 업로드는 구현하지 않았다 (v1.1 후보)

### 4.8 우선순위 (미구현, UI 자리만 확보)

```
        ↓

③ 제안 패널이 앱 위에 뜬다
   1. 발표자료 만들기  — 오후 발표 전까지 필요
   2. PR 리뷰         — 다른 사람이 기다리는 중
   3. 운동            — 시간대 자유
        [적용]  [취소]
        ↓
④ 적용을 눌러야 실제 순서가 바뀐다
```

**보내는 것**: 미완료 할 일, 오늘 날짜와 요일, 메모, 다가오는 일정. "메모도 함께 보내기" 토글을 두고 기본값은 켬.

**즉시 재정렬하지 않는 이유**: 목록이 갑자기 낯설어진다. 어디에 무엇이 있었는지 감각이 깨진다.

**페이지 이동을 하지 않는 이유**: 외부 AI 페이지에 프롬프트를 미리 채워 여는 것은 공식 기능이 아니라 언제든 깨진다. 더 중요하게는 **그것은 이미 `📋 복사` 버튼의 역할이다.**

| 버튼 | 역할 |
| --- | --- |
| 📋 복사 | ChatGPT로 **가서 대화한다.** 열린 질문 |
| ✨ 우선순위 | **여기서 순서만 정리한다.** 앱을 떠나지 않음 |

**API 키**: Supabase Edge Function을 경유한다. 클라이언트에 노출하지 않는다.

## 5. 화면 구조

```
┌──────────────────────────────────────┐
│  오늘의 작업 공간                     │
│  8월 1일 금요일       2/4      ◐     │
├──────────────────────────────────────┤
│  📌 다가오는 일정                     │
│     8/3   치과                       │
│     8/5   회식                       │
│     +4개 ▾                           │
├──────────────────────────────────────┤
│         2026년 8월 ›                 │
│  ‹  일  월  화  수  목  금  토  ›    │
│     26  27  28  29  30  31   1       │
├──────────────────────────────────────┤
│  ⠿ ☐ 발표자료 만들기             ✕   │
│  ⠿ ☑ PR 리뷰                     ✕   │
│  ＋ 할 일 추가                        │
├──────────────────────────────────────┤
│  📝 메모                             │
├──────────────────────────────────────┤
│  [📋 복사] [📅 다른 날짜로] [✨ 우선순위] │
└──────────────────────────────────────┘
```

### 반복해서 나온 문제: 위쪽 블록이 자리를 넓힌다

개발 중 "화면이 부담스럽다"는 판단이 세 번 나왔다. 지난 일정, 날짜 탭, 일정 블록. 모두 같은 원인이었다.

> **할 일 목록이 주인공이고 나머지는 거들어야 한다.** 할 일이 첫 화면 절반 아래로 밀리면 잘못된 방향이다.

무언가를 화면에 추가할 때는 **순서와 높이까지 함께 봐야 한다.** 개별 결정이 모두 옳아도 쌓아놓으면 서로를 가릴 수 있다.

### 또 하나의 원칙: 보이는 것을 누르면 그 자리에서 반응한다

두 번 겪었다. `+N개 ›`를 눌렀더니 달력으로 튀었고, 달력에서 날짜를 눌렀더니 화면이 바뀌었다. 둘 다 기대와 결과가 어긋났다.

> **화면에 이미 보이는 것을 클릭하면 그 자리에서 반응해야 한다.** 화면을 떠나는 것은 명시적인 이동 버튼일 때만.

`›`는 "다른 곳으로 간다", `▾`는 "여기서 펼쳐진다"로 읽힌다. 기호도 이 원칙을 따른다.

## 6. 데이터 모델

### 클라이언트

```ts
type Todo = { id: string; text: string; done: boolean };
type Day = { todos: Todo[]; memo: string };
type ScheduleItem = { id: string; date: string; text: string };

type AppState = {
  days: Record<string, Day>;   // key: "2026-08-01"
  schedule: ScheduleItem[];
  active: string;
};
```

**화면 상태 (저장하지 않음)**

```ts
type View =
  | { kind: 'week';  anchor: string }
  | { kind: 'month'; anchor: string }
```

### 서버 (Supabase / PostgreSQL)

```sql
create table user_state (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  data       jsonb not null default '{}',
  updated_at timestamptz not null default now()
);

alter table user_state enable row level security;

create policy "본인 데이터만"
  on user_state
  for all
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

**왜 통째로 저장하는가**

할 일 하나당 한 행으로 쪼개는 것이 정석이지만, 테이블 4개와 조인, 마이그레이션이 따라오고 개발이 일주일 늘어난다. 혼자 쓰는 단계에서는 통째로 저장이 명백히 이득이다.

**RLS**

권한 판단을 앱이 아니라 DB가 한다. 정책이 걸린 뒤에는 어떤 쿼리를 날려도 남의 행이 결과에 나오지 않는다. Oracle의 VPD와 같은 개념이며, 브라우저가 DB에 직접 접근해도 안전한 이유다.

**실제로 검증했다.** 다른 계정으로 로그인해 추가한 항목이 원래 계정에 보이지 않는 것을 확인했다. 초기에 남의 데이터가 보이는 것처럼 느껴졌던 것은 RLS 문제가 아니라 LocalStorage 캐시가 남은 문제였고, 로그아웃 시 캐시 삭제로 해결했다.

### 저장 규칙

- LocalStorage 키: `daily-check:v1`, 스냅샷은 `daily-check:snapshot`
- 쓰기는 350ms 디바운스
- 날짜 키는 **로컬 타임존 기준** `YYYY-MM-DD`. `toISOString()`은 UTC 변환으로 한국 시간 오전 9시 이전에 하루가 밀리므로 사용 금지
- 빈 날짜(할 일도 메모도 없는)는 `days`에 키를 만들지 않는다
- 저장소 접근은 `src/lib/storage.ts` 한 파일만 통과한다

## 7. 기술 스택

| 영역 | 선택 |
| --- | --- |
| 프레임워크 | React 18 + TypeScript |
| 빌드 | Vite |
| 스타일 | Tailwind CSS |
| 드래그 | dnd-kit |
| 로컬 저장 | LocalStorage (오프라인 캐시) |
| 인증·DB | Supabase (Google OAuth + PostgreSQL) |
| 배포 | Vercel |
| PWA | manifest + service worker |

### 서버 코드가 0줄인 이유

Supabase는 클라이언트 SDK로 브라우저에서 직접 접근한다. 백엔드 서버가 없으므로 앱은 정적 파일이고, 정적 호스팅에 그대로 올라간다.

### 자바(Spring)를 쓰지 않은 이유

주 언어가 자바이지만 백엔드 칸 자체가 없는 설계다. Spring Boot를 얹으면 서버 상시 구동, 인증 직접 구현, API 설계, 이중 배포 파이프라인이 따라온다. **기능은 동일한데 MVP가 일주일 넘게 늘어나고 비용이 0원을 벗어난다.**

목적이 "이 앱을 빨리 갖고 싶다"였으므로 현재 스택을 선택했다. 나중에 학습 목적으로 Spring 버전을 만들고 싶다면 `storage.ts` 한 파일만 교체하면 된다.

### 비용

| 항목 | 무료 한도 | 실제 사용량 |
| --- | --- | --- |
| Vercel Hobby | 월 100GB 전송 | 사실상 0 |
| Supabase DB | 500MB | 사용자당 수십 KB |
| Supabase 인증 | 월 활성 사용자 5만 | 1명 |

**합계 0원.**

**주의**: Supabase 무료 프로젝트는 **7일간 활동이 없으면 일시 정지**된다. 데이터는 유지되고 대시보드에서 재시작하면 30초쯤 걸린다. 매일 여는 앱이라면 걸릴 일이 없다.

## 10. 성공 기준

MVP 완성 2주 후 확인한다.

1. **매일 열었는가** — 열지 않았다면 마찰 지점을 찾는다
2. **복사 버튼을 실제로 눌렀는가** — 안 눌렀다면 이 앱의 전제가 틀렸다
3. **폰에서도 열었는가** — 안 열었다면 동기화에 들인 비용을 재평가한다
4. **다른 앱으로 돌아갔는가** — 돌아갔다면 무엇이 부족했는지 기록한다
5. **v1.1 후보 중 실제로 아쉬웠던 것은 무엇인가** — 이 목록이 다음 범위를 정한다

지표보다 중요한 판단 기준: **"내일도 이걸 열고 싶은가."**

참고로 Supabase 프로젝트가 7일 무활동으로 일시 정지됐다면, 그것은 인프라 문제가 아니라 1번에 대한 답이다.
